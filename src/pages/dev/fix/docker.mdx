**主機和容器是兩回事。** 主機是 Ubuntu、容器是 Alpine 時，PHP 跑在容器裡，就照這一頁處理，容器內的套件版本對照 [Alpine](/dev/fix/alpine/) 或 [Debian](/dev/fix/debian/) 頁；主機那一頁只管主機本身裝的 PHP。

## 1. 檢查

- 列出所有用到 PHP 的映像：官方 `php` 映像、以它為基底的自建映像、第三方應用映像（例如 WordPress、Drupal 官方映像）、廠商提供的映像。
- 在**正在接流量的容器**裡確認版本，不要只看建置機或本機的舊映像：

<CommandBlock label="在執行中的容器裡查版本（容器名、Pod 名換成你的）" code={`docker exec <容器名> php -v
kubectl exec <Pod 名> -- php -v`} />

## 2. 更新：重建映像

查詢時，官方 `library/php` 已有以下正式 tag：{facts.fixed.map((f) => f.version).join('、')}。變體包含 cli、apache、fpm、alpine、bookworm、trixie，以及對應的 ZTS。

- 把 Dockerfile 的基底改成已修補的版本，**釘到完整版號**（例如 {facts.fixed[1].version} 的對應變體），不要只寫 `latest` 或只寫分支號，才知道實際跑的是哪一版。
- 8.5.12 與 8.4.27 的查詢結果同時列出 RC1 tag，那不是這次的正式發行版，不要選到。
- 重建時拉取最新的基底映像，不要用到快取裡的舊層。
- 第三方應用映像：等上游重建並發布含修補 PHP 的版本，再更新你的 tag。

<CommandBlock label="重建時強制拉新的基底映像、不用快取" code={`docker build --pull --no-cache -t myapp:php-8.4.27 .`} />

抽查各版第一筆映像的推送時間：8.5.12 為 2026-10-21 23:26 UTC（台灣時間 10-22 07:26），8.4.27 為 23:31 UTC，8.3.36 為 23:28 UTC，8.2.35 為 23:27 UTC。這不是每一個 tag 的推送時間。

## 3. 重啟：重新部署

- 以新映像重新部署所有服務。只重建、沒有部署，跑著的還是舊容器。
- **Kubernetes**：更新 Deployment 等工作負載的映像版本並完成滾動更新；確認舊的 ReplicaSet 已縮到零，沒有還在接流量的舊 Pod。
- 確認編排檔、Helm values 或 CI 沒有把舊 tag 拉回來。

## 4. 驗證

- 在正在接流量的容器（每一種服務、每一個叢集）裡再跑一次 `php -v`，確認達到修補版。
- 核對執行中容器的映像版本，確認都是新建置的那一版。
