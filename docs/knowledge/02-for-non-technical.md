# 給非技術人員

你不需要會寫程式。這篇用餐廳來說明 PHP2Shell：它是什麼、為什麼很多網站突然關站、你自己會不會有事、以及網站如果是你負責的，現在該問誰。

數字、版本與時間的對照卡在 [總覽](00-overview.md)。名詞在 [術語表](05-glossary.md)。

## 先記三句

1. 問題在 **PHP 這個語言本身**，不在某一篇文章或某一個外掛寫錯。
2. **2026-10-21 晚上 10 點（台灣時間）修補已經發布。** 要更新的是伺服器上的 PHP，不是只按 WordPress 的「更新外掛」。
3. 很多網站關站，是因為來不及更新而先拉下鐵門。關站多半是預防，不是已經承認被偷資料。

## PHP 是餐廳廚房的主廚

把一個網站想成餐廳。

你看得到的版面、圖片、按鈕，像是裝潢和菜單。廚房裡還有一位主廚，叫做 **PHP**。你一點「送出」、一開「會員中心」，就是在點菜。主廚照著食譜（網站的程式）做事，向冰箱（資料庫）拿出你的訂單或文章，再把做好的頁面端回你的瀏覽器。

WordPress、購物車、學校報名表、公司官網，常常是不同的食譜，卻雇用同一種主廚。全球已知伺服器端語言的網站裡，大約 69.3% 用 PHP。（`news/2026-10-21-ithome-php-zero-day-storm-warning.md`、`news/2026-10-22-1010-hket-php-security-vulnerability.md`）

PHP2Shell 不是某一份食譜寫錯。是主廚的基本功出了問題，而且這個問題跟了很久。

主廚的工作台（記憶體）有大小限制。忙到工作台堆滿，或做到一半發生嚴重錯誤時，他可能只收拾一半就跳開。下一位客人如果還是分到**同一位主廚**（技術上叫同一支 worker），主廚可能把上一桌留下的紙條，當成這一桌的訂單。

遠端的人可以趁這個混亂，叫主廚去做菜單上沒有的事。嚴重時，等於讓外人使用餐廳的電腦。

就算這家店的食譜只有一行「你好」，只要端菜的人仍是這位主廚，問題仍可能發生在食譜被翻開之前。研究者用只回應一行字的程式說明過這一點。（`news/2026-10-21-2159-wiz-php2shell-ai-uncovers-rce.md`、`news/2026-10-21-2147-imperva-php2shell-oom-wrong-moment.md`）

## 什麼是 RCE

RCE 是 remote code execution，中文常說「遠端程式碼執行」。

翻譯成日常用語：人不用進你的機房、也不用先當會員，就有機會叫你的伺服器執行他要的指令。伺服器能做的事，他就可能做得到，例如讀走資料庫、放進一個以後還能進來的後門程式、或拿這台機器去做別的事。

官方給這次的嚴重分數是 CVSS v4.0 的 **9.2**（滿分不是 10 分這一套規則，新聞裡的「10 分」是外洩貼文的錯誤數字）。PHP 基金會的資安工程師 Volker Dusch 說，這是 PHP 十多年來最嚴重的問題，並拿 2014 年的 Heartbleed 來比：當年全球管理員也是緊急更新大批伺服器。（`news/2026-10-21-2240-cnyes-php-emergency-patch-heartbleed.md`）

它還有一種不必「完全接管」也已經很糟的後果：研究者展示可以讀到這支程式記憶體裡的密碼、金鑰與憑證，並且經由一個叫 `PHPSESSID` 的 cookie 送出去。網站程式即使沒有啟用會員登入，這件事仍可能成立。（`news/2026-10-21-2159-wiz-php2shell-ai-uncovers-rce.md`）

## 為什麼全球網站下線

因為換主廚需要時間，而漏洞已經被人知道。

- 修補在台灣時間 10/21 晚上 10 點才公開。前一天晚上，漏洞編號已經流到論壇上。
- 美國國家安全局建議：不能立刻更新的系統先下線。理由是這類漏洞往往有一條直達伺服器檔案或資料庫的路。（`news/2026-10-21-2009-bbc-websites-taken-down-worldwide.md`）
- 英國國家網路安全中心建議：緩解做不到或做得太慢，就先下線，並且在重新上線前檢查有沒有被裝後門。（`news/2026-10-21-ncsc-critical-security-issue-php.md`）
- 日本首相高市早苗在 X 上以很急的語氣，請大家確認公開網站是不是用 PHP。（`news/2026-10-22-1010-hket-php-security-vulnerability.md`）

所以你看到維基的部分功能停用、論壇改成只能看、政府網站暫時打不開，多半是店家自己拉鐵門。Mashable 的句子可以直接借用：下線不表示已經被入侵，下線是為了不要被入侵。（`news/2026-10-22-0232-mashable-php-vulnerability-websites-offline.md`）

還有一個容易誤會的地方。很多系統有「維護模式」開關，打開後畫面上寫「系統升級中」。電商安全公司 Sansec 說：**應用程式自己的維護模式擋不住**，因為問題發生在應用程式開始跑之前。有用的是網站伺服器直接改成靜態的暫停頁面，或乾脆不要對外。（`news/2026-10-21-sansec-php2shell-critical-rce.md`）

## 一般民眾會不會受影響

依目前的公開說明，可以這樣分：

**你的手機和家裡的電腦，不會因為「PHP 有漏洞」這件事本身就被入侵。** 洞在網站的伺服器上，不在你的手機作業系統裡。香港經濟日報的讀者問答也是這個方向。（`news/2026-10-22-1010-hket-php-security-vulnerability.md`）

**你在那個網站留下的資料，風險在伺服器端。** 若那台伺服器被控制，上面的會員資料、訂單、留言，都在對方可以碰到的範圍裡。鉅亨網編譯《華爾街日報》還提到：被接管的網站，有可能被拿去影響訪客，例如頁面被改掉。（`news/2026-10-21-2240-cnyes-php-emergency-patch-heartbleed.md`）這是「網站如果失守，訪客可能遇到被動過手腳的頁面」，不是「只要開過任何網頁就一定中獎」。

截至 2026-10-22，公開資料裡**沒有**一份完整的「哪些網站已經被偷走哪些資料」清單。關站名單不能當成受害名單。

實務上你可以做的很少，而且都是平常的習慣：

- 看到常去的網站在維護，先等它自己的公告，不要改去點私訊裡的「緊急更新」連結。
- 若該服務**明確公告已經遭入侵**，再依它的指示改密碼。沒有公告，不必因為恐慌而在每個網站重複使用同一組新密碼，更不要把密碼寄給任何人。
- 管這個網站的人是另一件事：更新之後，請管主機的人評估要不要更換網站相關的密碼與金鑰，特別是懷疑被入侵或曾長時間未更新。不要說成所有訪客都要改密碼。（`news/2026-10-21-php2shell-com-research-disclosure.md`）
- 網站防火牆、CDN、主機商的防護規則不能取代更新 PHP。對非技術讀者改說「防火牆、擋在前面的加速服務、主機商的防護規則，都不能代替把主廚換掉」。
- 突然有人私訊要付費「幫你檢測有沒有中 PHP2Shell」，當成詐騙處理。

## 網站老闆、主管、用虛擬主機的人

你可能不是自己管伺服器的人。責任仍可以分得很清楚。

**主管現在要做的決定：**

- 指定一個人回答：「我們有哪些系統用 PHP？」包含官網、舊的活動網站、報名系統、電商、以及廠商設備裡悄悄附帶的 PHP。資安署提醒，有些軟體表面沒寫 PHP，裡面仍在用。（`news/2026-10-22-moda-php-emergency-update.md`）
- 更新 WordPress、Drupal、Joomla、Magento 的「程式或外掛」，**不會**修掉這個洞。要更新的是底下的 PHP。（`news/2026-10-22-1105-billows-php-enterprise-response.md`）
- 若主機商或廠商今天給不出「已經更新並重啟」的證據，而網站又直接開在網路上，就要認真考慮先下線。英國 NCSC 與美國 NSA 的建議都是這個方向。這是業務決策，不是技術細節。
- 問維運：日誌至少從 **2026-10-17** 看起，不是從新聞出來的 10/21 才看。Amazon 的蜜罐在 10/17 就看到有人嘗試。（`news/2026-10-22-0636-aws-php2shell-exploitation-madpot.md`）
- 若有人懷疑已經被入侵：先隔離、把日誌留下來，**不要急著整台重灌**。重灌會把證據清掉。

**用虛擬主機、主機代管、或「網站是廠商幫我們放的」：** 你多半沒有權限自己換 PHP。把下面的問題貼給主機商或廠商，請他們逐題回覆。回覆裡若只有「我們有資安防護」而沒有版本號，那題就算沒答。

### 給主機商的問題清單

1. 我這個網站實際跑的 PHP 是哪一版？請給出版號，以及它是 php.net 官方版、還是 Linux 發行版回移植的套件版。
2. 用的是 Apache 的 mod_php、PHP-FPM、LiteSpeed、php-cgi，還是別的？官方認為 mod_php 風險最高。
3. 修補裝了沒有？目標是 8.5.12、8.4.27、8.3.36 或 8.2.35；若是發行版套件，請給出安全公告或套件更新紀錄，不要只說「已經是最新」。
4. 所有 PHP worker 重啟了沒有？只上傳檔案、沒有重啟，舊的行程可能還在服務。
5. 若版本是 8.1、8.0、7.4：有沒有官方或發行版的回移植？若是 7.3 或更舊：升級時程是哪一天？升級前網站是否已不直接對網際網路開放？
6. 修補前有沒有做官方的暫時措施？修補之後，若曾把記憶體上限關掉（`memory_limit=-1`），是否已改回合理的值？
7. 從 2026-10-17 到現在的紀錄裡，有沒有大量的錯誤、PHP 行程自己重開、異常巨大的 `PHPSESSID`、或網站目錄突然多出的 PHP 檔？
8. 備份是否同時包含網站檔案與資料庫，而且備份不是放在同一台還能被寫入的機器上？
9. 若是 Docker 或廠商給的映像檔：映像是否已用修補過的 PHP 重新建置並部署？主機作業系統更新不會自動換掉映像裡的 PHP。
10. 有沒有 WAF（例如 Cloudflare）？有的話請同時確認 PHP 本身已更新。WAF 是多一層過濾，不是修補。
11. 若發現可疑：可否協助保留網頁與 PHP 日誌、先不要重灌，並通知我們？

ICSDA 建議台灣時間修補釋出後，盡快完成四件事：更新 PHP、重啟服務、確認版本、檢查紀錄。（`news/2026-10-21-1357-icsda-php2shell-patch-released.md`）

## 常見問題

**我只是用 WordPress，按更新就好了嗎？**  
不夠。外掛和佈景的更新修的是食譜。這次要更新的是主廚，也就是伺服器上的 PHP。虛擬主機通常要主機商做。

**打開「網站維護中」有用嗎？**  
網站程式自己的維護模式沒用（Sansec）。要嘛主機商更新 PHP，要嘛在網頁伺服器層改成靜態暫停頁、或先不要對外。

**主機商會自動幫我更新嗎？**  
不一定。有的主機會等你開單，有的套件庫（remi）官方說當天不會更新。用問題清單要一句明確的版本回覆。

**新聞說 10 分滿級，是真的嗎？**  
官方分數是 9.2。10 分來自漏洞編號外流時的錯誤訊息。9.2 已經是「請立刻處理」的等級，不需要等一個更高的數字。

**我們是不是已經被駭了？**  
不一定。關站與搶修是預防。另一方面，10/17 就有人對誘餌系統嘗試攻擊，所以「新聞才剛出來、應該還沒人會打」這個假設不成立。有沒有打到你，要看日誌，不能靠感覺。

**手機 App 要更新嗎？**  
若 App 只是裝在手機裡、後端不是 PHP，這次漏洞不在 App 本身。若 App 的伺服器是 PHP，要更新的是那台伺服器。個別服務是否使用 PHP，看該服務的公告。沒有公告就不要自己猜測它被入侵。

**台灣政府有動作嗎？**  
有。數位發展部資通安全署 2026-10-22 發新聞稿，已透過資安警訊、國家資安資訊分享與分析中心（N-ISAC）及 TWCERT/CC 通知各機關與企業，請盤點、修補、並檢查日誌與異常登入。（`news/2026-10-22-moda-php-emergency-update.md`）

**舊活動網站放著不管可以嗎？**  
不行。舊站、測試站、廠商當年交的報名系統，只要還連得上，就一樣算。CyberQ 引述的統計裡，有露出版本號的主機約 59% 跑的是沒有官方修補的舊版。舊站往往正是這一群。（`news/2026-10-21-0852-cyberq-php-core-rce-leak.md`）

**可以請人「順便測試看看打不打得進去」嗎？**  
不要對還在用的網站做攻擊測試，也不要從網路下載號稱 PHP2Shell 的工具。那類工具會幫倒忙，也可能違法。請主機商更新，並依上一節的問題清單留證據。

**訪客會被看光密碼嗎？**  
有這個風險方向：研究者展示伺服器記憶體裡的密碼與金鑰可以被讀出。這不表示每一個網站都已經發生。若你在該站的密碼也用在別的地方，而該站公告遭入侵，就把那些重複使用的密碼換掉。
